# What the planner can actually do

> Measured on 2026-11-23, on 11 controlled scenarios against eShopOnWeb, Microsoft's sample shop, which nobody here wrote, with the published demo account stored as the test account, so exploring signs in (ADR-0033), 2 execution(s) each. Generated by `tools/Autestiq.Benchmark`.

## How to read this

**The baseline is a plan a person wrote**, in the same vocabulary, run by the same executor.
So the only difference between the columns is who chose the actions. A baseline written as
Playwright code would also differ in how it waits and how it locates, and the table would be
comparing two things at once.

None of the 11 scenarios has a defect to catch: this application has no defect switches, so every scenario runs against it as it is, where passing is correct. The set measures one mistake only, reporting a defect in an application that has none. How many defects are caught is measured on the other sets.

The asymmetry between the two mistakes is the whole point of measuring. A false negative costs
a person an afternoon. A false positive converts an absence of testing into an assurance of
quality, which is worse than having no tests at all, because somebody then ships on it.

**"Detected nothing" is a third outcome, and it exists because the first real measurement
needed it.** A plan that fails the broken shop *and* the sound one has not found the defect;
it fails at everything, and one of the things it fails at happens to be broken. Counting
those as correct verdicts turned "one defect genuinely caught out of six" into "five of six",
which is the sort of number a benchmark exists to prevent.

**A plan that covers part of a scenario and passes that part is inconclusive, not passed.**
The planner says how much it covered, in a field rather than in prose, and a partial plan
whose every step passes ends as inconclusive. The first real measurement had plans that
honestly reported testing half of what was asked and were then counted as passes, which is
an assurance wider than the evidence — the same mistake as a false positive, arrived at
politely.

Flake is measured across repeated **executions** of the same plan, so it describes the
application and our runner, not the model's variation between answers. That is a different
question and it is not answered here.

## What the planner and the validator had to say

- **second-page-holds-the-last-two**: Page 2 of the catalogue is reached at /?pageId=1 (pageIds start at 0). The crawl showed this page labelled 'Page 2 - 2'. I went there directly because the Previous/Next links appear twice on the page and would not name a single element.
- **second-page-holds-the-last-two**: The product on page 2 is spelled 'Prism White TShirt' with no hyphen, while page 1 has 'Prism White T-Shirt'. I used the spelling from the description and the page 2 crawl.
- **catalogue-shows-a-price**: The crawl could name the price only as the text "19.50" with no "within", because it is the only element on the catalogue page with that text. The plan therefore checks that "19.50" is visible, and separately that the product name is visible. It does not check that the two sit in the same product card.
- **catalogue-shows-a-price**: The crawl's basket page for this product shows "$ 19.50", which is consistent with the catalogue price.
- **adding-a-product-opens-the-basket**: The basket item count is read from the header basket link, which the crawl shows as "1" after one item is added (it is "0" on an empty basket).
- **adding-a-product-opens-the-basket**: The /Basket path after the click comes from the crawl, which reached /Basket by exactly this step.
- **two-products-are-both-in-the-basket**: The basket page crawled after adding two items shows the item count as a link named "2", so that link is used to check the count of two.
- **two-products-are-both-in-the-basket**: The .NET Blue Sweatshirt basket row was not crawled. It is assumed to appear as text with the product name, like the other rows.
- **two-products-are-both-in-the-basket**: The return to the catalogue uses the "eShop On Web" header link, the route the crawl took to get back to the catalogue.
- **an-empty-basket-says-so**: The empty basket page was crawled at /Basket with the heading "Basket is empty.", so the plan opens that path directly with nothing added.
- **an-empty-basket-says-so**: Also asserts that the [ Checkout ] link is not offered, which follows from the empty-basket page shown (it has no Checkout link).
- **checkout-asks-to-sign-in**: The check that you are asked to log in is the 'Log in' heading, which the crawl found on the login page. I did not assert the URL after the redirect, because no page shown to me gives it. It is probably /Identity/Account/Login with a return URL, but that is a guess.
- **wrong-password-is-refused**: The wrong password 'not-the-password' is typed as plain text because it is deliberately incorrect, not a real credential.
- **wrong-password-is-refused**: The refusal is checked by the 'Invalid login attempt.' message that the crawl saw after a failed login, and by the Log in heading still being shown, which means the user was not taken to another page.
- **wrong-password-is-refused**: No URL assertion is made after the attempt because the path after a refused login was not shown in the crawl.
- **signing-in-shows-who-is-signed-in**: The Email field is filled from the stored secret 'username', on the assumption that it holds demouser@microsoft.com, the address in the description.
- **signing-in-shows-who-is-signed-in**: The signed-in check looks for the exact text demouser@microsoft.com, taken from the description. The crawl shows the signed-in address only as the redacted placeholder [secret:username]. If the stored username is a different address, this check will fail.
- **signing-in-shows-who-is-signed-in**: I did not assert the URL after login, because no page shown to me gives it.
- **signing-in-shows-who-is-signed-in**: The step “The page shows the signed-in user's email” acts on the text “demouser@microsoft.com”, which was not on any page the crawl saw. That is normal for something that appears only once the test has acted, and a mistake otherwise.
- **an-order-can-be-placed**: Assumption: after logging in, the shop sends the user on to the checkout page. The crawl never saw this, so the plan waits for the '[ Pay Now ]' button there. If login lands somewhere else, the plan will fail at that wait.
- **an-order-can-be-placed**: The description names demouser@microsoft.com. The plan types it through the stored 'username' secret and assumes that secret holds this address.
- **an-order-can-be-placed**: The crawl saw the test account's basket already holding other items. Pay Now would then buy those too. The plan only checks the thank-you message, so this does not affect it.
- **an-order-can-be-placed**: The tester gave /Basket/Success as the path, and the crawl never reached that page. The URL and message checks follow the tester's wording.
- **order-history-needs-sign-in**: No crawled page links to the order history, because the link only shows once logged in. The path /Order/MyOrders is my assumption, taken from how eShopOnWeb is normally laid out. If the application uses another path, the goto step has to change.
- **order-history-needs-sign-in**: I did not assert the exact URL after the redirect. The login page the crawl saw was /Identity/Account/Login, but a redirect would probably add a returnUrl query, and I have not seen that wording. Instead the plan checks for the 'Log in' heading and button, which the crawl did see on the login page.
- **forgotten-password-is-confirmed**: The confirmation is checked through the heading 'Forgot password confirmation' and the text 'Please check your email to reset your password.', both of which appear on the confirmation page the crawl reached after submitting the form.
- **forgotten-password-is-confirmed**: The plan does not assert the URL of the confirmation page. The crawl did see /Identity/Account/ForgotPasswordConfirmation, but the description did not ask for a URL check.
- **forgotten-password-is-confirmed**: The plan cannot check that an email is actually delivered; it only checks the confirmation shown in the application.
