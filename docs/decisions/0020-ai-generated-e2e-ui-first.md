# 0020 — AI-generated end-to-end UI tests first; everything else follows the measurement

- **Status:** Accepted
- **Date:** 2026-11-15

**Result, on the demo shop (2026-11-15):** the held-out set of twenty scenarios passed the gate:
50 of 52 runs correct, 38 of 40 on the sound shop (the two misses were inconclusive, on one discount-code
scenario), 12 of 12 on the broken shop, no false positives, no flakes. Recorded in
`docs/ai-benchmark-held-out.md`. The result is for one application only. The gate is not met for any
other application until it has been measured on one (see the second target in `tools/Autestiq.Benchmark`).

## Context
The owner's thesis: a company reduces its QA team by using Autestiq across the QA journey. The
first step is end-to-end UI tests, generated by AI. Later steps are API, performance, database,
security and penetration testing, then hardware testing. Every QA artifact (strategy, test cases,
suites, reports, documentation, analysis) is to be produced by AI.

The measurement so far says the planner is not yet reliable enough to sell (ADR-0019 and
`docs/ai-benchmark.md`: 5 of 12 plans passed a working application; 1 of 6 defects caught). Four
fixes followed, and none has been re-measured. A model key is not available in this environment.

## Decision
1. **The first product is AI-generated E2E UI testing of a web application.** Plans are generated by
   the model once, from the closed action vocabulary, and validated against what the crawl observed
   (ADR-0019). A deterministic executor runs them. The model is never in the execution loop.
2. **Expansion is gated by measurement, not by the roadmap.** API, performance, database, security
   and penetration testing are not started until the E2E UI generator meets the validation gate
   below on measured data.
3. **Every AI-generated QA artifact is derived from recorded evidence.** A generated test case, suite,
   report, analysis or strategy records the run identifiers, observations and model version it was
   built from. A generated sentence that asserts an outcome must link to the evidence for it. A
   statement that cannot be linked to evidence is not shown as a finding. This is Risk 01 of the
   directive, applied to documents.
4. **A human approves material changes.** Generated test definitions and any change to an existing
   test are approved before they run. Nothing in the product calls a model without a budget
   (ADR-0019 §6, and per-organization limits when they exist).
5. **Hardware testing is a long-term vision and is not designed here.** It needs physical devices,
   safety boundaries and a different execution model. Nothing in this repository prepares for it
   beyond keeping the execution boundary general.

**The clean measurement: Spring PetClinic (set up 2026-11-23, not yet run).** eShopOnWeb's figures came after
changes made on its own results, so the owner chose a second application nobody here wrote or tuned on: Spring
PetClinic (Java, server-rendered), at commit `500158f` of `spring-projects/spring-petclinic`. The protocol:
1. **Written before anything ran.** Eleven scenarios and their baselines (`tools/Autestiq.Benchmark/PetclinicScenarios.cs`)
   were written from the application's source, read and never run here.
2. **Frozen.** The explorer, the prompt and the validator stay as they are at the commit that adds the scenarios until
   the first planner run is published. Nothing changes in answer to PetClinic's results before then.
3. **Baselines checked with no model first.** A run without a key shows whether each hand-written baseline passes the
   application. A baseline that fails may be corrected, and the correction is reported; a scenario's words may not change.
4. **One planner run, published as it comes,** whatever it says (`docs/ai-benchmark-petclinic.md`).

**Result (2026-11-23, the owner's run, Claude Sonnet 5.5): 20 of 22 runs correct (91%), no false positive, no false
negative.** All eleven baselines passed the application unchanged, so no baseline was corrected. Model cost: $0.47.
- **The two runs without a verdict** are "a shared last name lists both owners": the search box has no label, so the
  plan listed every owner and checked both Davises among them, and said, as a partial plan, that the filtering was
  not tested. It was counted inconclusive, as it should be.
- **The unlabelled search box** (`use=none`) was handled three ways: opening the search's address
  (`/owners?lastName=Zygmunt`, inferred from what the crawl saw), listing all owners and following a link, or
  stopping at partial. None of them typed into the box.
- **Two passes are weaker than "correct" suggests**, and the set cannot tell, because it has no broken application to
  fail:
  - "Finding one owner opens their page" listed all owners and opened George Franklin's link. Its own note says "the
    search-by-last-name filtering itself is not exercised", yet the plan said it covered the whole scenario. That is
    a plan claiming more than its checks, the mistake partial coverage exists to prevent, here caught only by
    reading the notes.
  - "An edited address is kept" may pass without proving the edit. The benchmark runs the baseline before the
    planner explores, so the crawl already saw Jeff Black at 99 Orchard Lane, and the planner said so: "the final
    address check could pass without proving the edit worked". This is a flaw in how the benchmark orders runs on an
    application it cannot reset, not in the plan.

  Counting those four runs as unproven, the strict figure is 16 of 22. Both figures are given here; neither is a
  false positive.

**What this supports.** On one application nobody here wrote or tuned for, measured cleanly, with scenarios written
from its source before any run, the planner gave a correct verdict on 91% of runs on a sound application, with no
false positive. It does not support a claim about catching defects there (PetClinic has no defect switches), about
applications in general (it is one small application, eleven scenarios, one run), or about read-only exploration (the
benchmark explores with acting allowed, as our own applications are).

**After publishing, and only now, proposed fixes:** run the planner's exploration before a scenario's baseline on an
application that cannot be reset; and look at why a plan can call itself full while its own note says part was not
tested.

**The first is built (2026-11-23).** The benchmark now explores and plans every scenario before it carries any out,
so no exploration sees what a baseline or a plan changed. On our applications, which are put back before each
exploration, the order changes nothing: a replay of the hand-written plans as recorded answers gave the same verdicts
as before (the demo shop: 36 of 36 in both columns, defects on and off). What remains on an application that cannot be
put back: explorations still see what earlier explorations did, because exploring may act. Every figure above was
measured with the old order; the PetClinic figure is not re-measured.

**What this supports, and what it does not.** It supports this statement: *on our three benchmark
applications, on scenarios written after the planner was frozen, the planner's tests gave the right verdict
on 95% of sound-application runs, caught every seeded defect where a verdict was reached, and never passed
a broken application.* With the run without test ids, the same holds when the
applications carry no test ids. It does not support a claim about applications we did not build, or
customers' applications: those are measured next (eShopOnWeb, then a real site with its owner's permission),
and sales material says nothing broader until they are.

**Validation gate (confirmed by the owner on 2026-11-15):** before the first paid pilot, the planner
is re-measured on the benchmark, with more scenarios than the current 12, and a published result is
required that shows at least:
- a correct verdict on at least 90% of sound-application runs, and at least 90% of seeded defects
  caught where a verdict is possible;
- zero false positives on sound applications across the repeated runs;
- a flake rate and a cost per run, both published next to the deterministic baseline.

Until that result is published, no sales material claims that the product generates reliable tests.

## Consequences
- **Easier:** one product, one claim to measure, and a clear order of expansion.
- **Harder:** the first customer depends on the planner's reliability, which is unproven. The
  benchmark must be run on a developer machine with a key (`PLANNER__APIKEY=… dotnet run --project
  tools/Autestiq.Benchmark`) and the result committed.
- **Must remember:** "replace QA staff" is the owner's thesis. It is a hypothesis to test with
  customers, measured as time saved, as the directive asks (§2.2, §12). It is not a product claim.
- The module milestones (Milestone 5) are narrowed to what the first product needs: projects,
  environments, AI-generated test cases and suites, run history and reports. The other modules wait.

## Alternatives considered
- **Customer-authored scenarios first, AI later.** Lower risk and earlier revenue, but it abandons
  the thesis the owner asked us to test. Kept as the fallback if the validation gate fails: it is
  the same executor with a different plan source.
- **Build the whole ISTQB journey first** (Milestone 5 as written). Rejected: it is mock UI for a
  product no customer has used, which the directive names as the overcomplexity risk (R-10).
- **Start with API or security testing.** Rejected for now: each needs its own vocabulary and
  threat model, and the E2E path is the one already built.
